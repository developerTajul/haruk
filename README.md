# DLS Starter Plugin

A modular, lightweight WordPress plugin foundation for integrations and other small-to-medium plugins. It targets PHP 8.1+ and uses Composer's PSR-4 autoloader; WordPress is the runtime platform, and there are no external runtime package dependencies by default.

## Architecture

### Two-tier, container-ready design

The default architecture is deliberately small: feature modules call WordPress APIs directly, while shared support classes encapsulate common option access, template rendering, and validation. The optional `core/Database/` tier provides repositories for custom-table or database work and can be omitted when an integration does not need it.

There are no external runtime dependencies in the default setup. If the project later needs a dependency-injection container, `devlinkstudios/wp-service-container` is an upgrade path, not a package currently required by this plugin. `DevlinkStudios\StarterPlugin\Bootstrap\Plugin::resolveModule()` is the composition point: replace its current `new $moduleClass()` construction with container resolution and bind module dependencies there. Keep modules usable without the container if that remains a project requirement.

### Context-aware bootstrapping

`Plugin::init()` resolves modules for the current WordPress request and registers each module through `ModuleInterface::register()`:

- `AdminModule` is resolved only when `is_admin()` is true.
- `FrontendModule` and `RestApiModule` are resolved on every request.
- `AjaxModule` is resolved only when `DOING_AJAX` is true.

Module constructors accept dependencies and do not register hooks. A module owns its hooks, handlers, and assets. This makes features easier to reason about and allows unused modules to be removed without moving their responsibilities into a central controller.

### Pluggable module isolation

Each feature lives under its own `core/Modules/{ModuleName}/` directory and implements `DevlinkStudios\StarterPlugin\Contracts\ModuleInterface`. Register all WordPress hooks inside `register(): void`; keep database access in repository classes, render templates through `Support\View`, and use prefixed names for options, hooks, constants, and REST routes. To trim a feature, remove its module directory and its `use` statement / resolution entry in `core/Bootstrap/Plugin.php`. Also remove that feature's views or assets if they are no longer used. Do not remove shared support or contract classes while another feature still uses them.

## Quick start

### 1. Install Composer autoloading

Run this from the plugin root:

```sh
composer install
```

The plugin entry file loads `vendor/autoload.php`. Composer maps `DevlinkStudios\StarterPlugin\` to `core/` using PSR-4.

### 2. Preview a rebrand

The CLI accepts both `--key=value` and `--key value` forms. Preview first; dry-run reports each file's exact token substitutions and the plugin entry-file rename without changing files:

```sh
composer rebrand -- --dry-run --name="DLS HubSpot Sync" --slug=dls-hubspot-sync --vendor=devlinkstudios --vendor-namespace=DevlinkStudios --namespace=HubSpotSync
```

`--vendor-namespace` is optional. When omitted, hyphen- or underscore-separated vendor segments are converted to StudlyCase. The vendor slug itself must be lowercase letters/numbers separated by single hyphens. The plugin slug follows the same pattern, and `--namespace` must be a StudlyCase PHP identifier.

### 3. Apply the rebrand

After reviewing the preview, run the same identifiers with `--clean` to apply replacements, rename `dls-starter-plugin.php` to the new slug's PHP filename, regenerate optimized Composer autoload files, and remove `bin/rebrand.php` only if Composer succeeds:

```sh
composer rebrand -- --name="DLS HubSpot Sync" --slug=dls-hubspot-sync --vendor=devlinkstudios --vendor-namespace=DevlinkStudios --namespace=HubSpotSync --clean
```

Do not use `--clean` when you want to keep the rebrand tool for subsequent changes. Rebranding rewrites tracked `.php`, `.json`, and `.md` files outside `vendor/`, `.git/`, and `bin/`; review and commit the resulting changes as appropriate.

### Rebranded token reference

| Starter token | Rebranded value | Example |
| --- | --- | --- |
| `DevlinkStudios\StarterPlugin` | `{StudlyVendor}\{StudlyNamespace}` | `DevlinkStudios\HubSpotSync` |
| `devlinkstudios/wp-starter-plugin` | `{vendor}/{slug}` | `devlinkstudios/dls-hubspot-sync` |
| `DLS_STARTER_` | `{UPPER_SNAKE_SLUG}_` | `DLS_HUBSPOT_SYNC_` |
| `dls_starter_` | `{lower_snake_slug}_` | `dls_hubspot_sync_` |
| `dls-starter-plugin` | `{slug}` (text domain / plugin slug) | `dls-hubspot-sync` |
| `dls-starter/v1` | `{slug}/v1` (REST namespace) | `dls-hubspot-sync/v1` |
| `DLS Starter Plugin` | `{name}` | `DLS HubSpot Sync` |
| `DLS Starter` | `{name}` | `DLS HubSpot Sync` |

The rebrander changes exact starter tokens in its mapping. It does not infer or rewrite arbitrary identifiers outside those tokens.

## Extending the plugin

All examples below use the starter identifiers so the rebrander can update them consistently. Add `declare(strict_types=1);` to each PHP file and follow WordPress escaping and input-sanitization conventions at the point of output/storage.

### Create a module

Create a class under `core/Modules/Example/ExampleModule.php`, implement the contract, then import and resolve it in `Plugin` for the request contexts where it is needed:

```php
<?php

declare(strict_types=1);

namespace DevlinkStudios\StarterPlugin\Modules\Example;

use DevlinkStudios\StarterPlugin\Contracts\ModuleInterface;
use DevlinkStudios\StarterPlugin\Support\Options;

final class ExampleModule implements ModuleInterface
{
    private Options $options;

    public function __construct(?Options $options = null)
    {
        $this->options = $options ?? new Options();
    }

    public function register(): void
    {
        add_action('init', [$this, 'registerShortcode']);
    }

    public function registerShortcode(): void
    {
        add_shortcode('dls_starter_example', [$this, 'render']);
    }

    public function render(): string
    {
        $enabled = (bool) $this->options->get('example_enabled', false);

        return $enabled ? esc_html__('Example enabled', 'dls-starter-plugin') : '';
    }
}
```

Constructors should only accept dependencies; hook registration belongs in `register()`. Prefer a module-owned view and module-owned assets when a feature has presentation or scripts/styles.

### Read and write options

`Options` adds the `dls_starter_` prefix automatically and avoids adding it twice when the supplied key already has that prefix:

```php
use DevlinkStudios\StarterPlugin\Support\Options;

$options = new Options();
$options->set('integration_enabled', true);
$enabled = (bool) $options->get('integration_enabled', false);
$options->delete('dls_starter_integration_enabled'); // Already-prefixed key is accepted.
```

### Render isolated templates

Templates resolve beneath the plugin's `views/` directory. `View::render()` outputs the template; `View::make()` returns its rendered string. Data is extracted with `EXTR_SKIP` in a static closure, isolating templates from controller object scope. Escape values in the template for their output context:

```php
use DevlinkStudios\StarterPlugin\Support\View;

View::render('example/message', [
    'message' => __('Welcome to DLS Starter Plugin', 'dls-starter-plugin'),
]);

$html = View::make('example/message.php', ['message' => $message]);
```

For example, `views/example/message.php` can safely escape a text value as `<?php echo esc_html($message); ?>`. The `.php` suffix is optional. Template paths containing `..` are rejected.

### Validate request data

`FormValidator` supports `required`, `email`, `numeric`, and `max:{len}` rules and exposes field errors:

```php
use DevlinkStudios\StarterPlugin\Support\FormValidator;

$validator = new FormValidator();
$isValid = $validator->validate(
    ['email' => $email, 'company' => $company],
    ['email' => 'required|email|max:254', 'company' => 'max:120']
);

if (!$isValid) {
    $emailError = $validator->firstError('email');
    $allErrors = $validator->errors();
}
```

Validation does not replace nonce, capability, sanitization, or output-escaping checks; apply those in the request handler as appropriate.

### Extend the database repository

Use `BaseRepository` only when the feature needs a custom table. Return an unprefixed table suffix from `tableName()`; the base class adds the WordPress table prefix and `dls_starter_`. Its query helpers are protected for use by concrete repositories:

```php
<?php

declare(strict_types=1);

namespace DevlinkStudios\StarterPlugin\Database;

final class ExampleRepository extends BaseRepository
{
    protected function tableName(): string
    {
        return 'records'; // Full table: {$wpdb->prefix}dls_starter_records.
    }

    public function find(int $id): ?object
    {
        return $this->findById($id);
    }

    public function count(): int
    {
        return $this->countAll();
    }

    public function delete(int $id): bool
    {
        return $this->deleteById($id);
    }
}
```

Dynamic query values must be prepared; table identifiers must remain trusted and validated. Keep `$wpdb` access inside repositories, not in modules, REST callbacks, or controllers.

## Included modules

- **Admin:** `dls-starter-plugin` menu/settings screen, guarded settings save handler, and admin-only assets.
- **Frontend:** `[dls_starter]` shortcode; frontend assets are registered normally and enqueued when the shortcode renders.
- **REST API:** public `GET /wp-json/dls-starter/v1/status` and API-key / administrator-protected `POST /wp-json/dls-starter/v1/webhook`.
- **AJAX:** authenticated and public `dls_starter_action` handlers protected by a WordPress nonce.

Review `docs/ai-plans/starter-plugin-blueprint.md` for the implementation plan and `docs/ai-reports/DECISIONS.md` for decisions recorded while building the starter.
